# 屏幕共享式陪练 · 候选交互

日期：2026-11-02。来源：用户反馈当前“指导”别扭，本质仍像对话，希望参考视频会议屏幕共享。

状态：讨论提案，见T51/A45与ADR-033；未获接受，不替代现有PRODUCT条款，不表示已经实现持续共享或实时语音。

可交互概念源码 `prototypes/shared-screen-companion.html`（本地讨论稿里的相对路径；本仓库没有该文件，因此不保留会失效的链接）用合成图片编辑器演示开共享、直接操作、错误格式提醒、安静尝试、暂停与结束；回应和短延时均为预设，无真实识屏、录音、模型调用或文件导出。对话中可直接体验；它用于讨论节奏，不代表最终工具条尺寸或真实响应速度。

## 判断：把一段共同操作作为基本单位

当前用户需要发消息、读回复、执行操作、再发“下一步呢？”。截图和指引已经落在真实软件上，但推进责任仍主要在用户：用户既要做任务，也要向Agent报告任务进度。共享屏幕的吸引力在于双方拥有持续的现场上下文，用户可以边做边说、随时插话，操作结果本身也能推进教学。

对话仍然有用：表达目标、解释原因、澄清歧义。候选变化是让对话服务于眼前的任务，而不要求每次操作都形成一个聊天轮次。主场是用户正在用的软件，Teach-me提供陪练状态、短提示和指点；历史放进回看入口。

事实依据：`src/host/main.ts`的continue动作调用input.prepare/submit，把continueText作为消息发送；`src/core/session.ts`管理消息、wait与ack；`src/renderer/Panel.tsx`显示“轮到你了”“正在等你回应”。ADR-023已允许按需主动capture，但这不等于持续观察。上述结构说明当前交互以消息为中心，不能据此推断每位用户的主观原因。

## 建议体验

1. **开始一段陪练。** 用户选择本次共享范围，说“陪我把这张图导出为PNG”。小工具条持续显示共享对象、观察状态、插话、暂停和结束；初版若只支持选屏，就如实标为选屏，不假装支持单窗口共享。
2. **屏幕上只留当前一步。** Agent短句“点右上角导出”，同时指向位置。用户操作时提示不抢焦点，不自动展开大段历史。语音输出可选，字幕始终可读。
3. **从新画面接着教。** 用户打开导出面板，旧指引先失效；新画面确认后提示“格式选PNG”。完成证据充分就接着走，正常路径不要求反复发送“下一步”。像素变化或一次点击本身不能证明完成。
4. **允许自然插话。** “等一下”“为什么选这个”“我这里不一样”优先于旧计划。立即停止旧播报和指引，重新对齐当前问题；取消不了的旧推理结果也不能迟到覆盖新现场。
5. **允许安静操作。** “我先试试”让Agent停止主动催促，保留共享；“暂停共享”则停止新采集与传输。两者含义必须明确。麦克风开关与共享开关也各自独立。
6. **结束时回顾。** 收起指引，停用采集/麦克风，按需给出已完成事项和可回看的步骤。是否保存回顾另行决定，不顺势引入跨重启会话持久化。

以“导出PNG”为例的节奏：

| 用户在做什么 | Agent何时回应 | 屏幕表现 |
| --- | --- | --- |
| 说出目标，继续停留在图片编辑器 | 看过当前画面后给第一步 | 导出按钮旁出现短提示 |
| 点击导出，面板出现 | 新画面稳定且确认是目标面板后 | 旧箭头消失，标出格式选择 |
| 自己调整选项 | 默认留白；明确偏离目标时简短提醒 | 不逐次播报每个鼠标动作 |
| 说“为什么选PNG？” | 立即停止旧播报，回答问题 | 可在原处解释，当前目标保留 |
| 导出完成 | 看到成功证据后确认；看不准才问 | 一句结果与可选回顾 |

默认建议“陪我做”，根据明确结果续接；需要慢节奏时选择“一步一步教”，操作完成后由用户确认再继续。不要让用户在大量模式里配置教学策略。

## 什么时候开口，什么时候不说

| 情况 | 候选规则 |
| --- | --- |
| 明确完成当前步骤 | 基于新证据给出下一步，不需要额外用户消息 |
| 明确偏离当前目标或出现错误 | 一句具体提醒，允许用户忽略或解释 |
| 画面变化但原因不明 | 撤下可能过期的定位；先重新观察，必要时只问一个问题 |
| 用户停顿 | 停顿可能是在阅读或思考，不自动判定卡住，也不按计时反复催促 |
| 用户说“我卡住了” | 中断旧计划，核对当前画面，缩小到一个可执行动作 |
| 用户说“我先试试” | 保留共享，停止主动续讲；用户求助后恢复 |
| 暂停共享、断连、切换共享范围 | 停止推进、撤下旧定位，明确“共享已暂停”或“连接中断”；恢复后先取新画面 |
| 结束会话 | 停采集、停音频、清指引和待处理观察；旧结果不得重新出现 |

## 观察与发言应当分开

候选观察机制是在明确的本次共享授权内，利用画面变化、操作结束和画面稳定等信号挑选关键帧，再把相关新证据交给现有Agent；连续画面变化需要合并，忙碌时保留最新相关现场，用户的问题和打断不能被合并丢弃。后台在采集不等于Agent已经理解，状态不能一律显示“我正在看”。

2026-11-02用户追问“Agent要不断读图吗”。需要反复获得新的视觉证据，才可能自动跟上操作；“持续共享”不等于让模型逐帧分析。候选拆成三层，尚未实现：

| 层次 | 做什么 | 边界 |
| --- | --- | --- |
| 本地观察 | 在已授权范围内监听可用变化事件，或比较低分辨率采样；合并拖动、滚动和动画期间的连续变化 | 只产生“可能需要看”的信号，不理解任务完成与否；本地采样仍算屏幕采集，暂停必须停止 |
| 观察调度 | 首次共享、用户提问、相关画面变化后稳定等时刻，选择当前帧及必要的前后对照；限制分析并发、去重和合并积压 | 忙碌时优先保留最新稳定现场及少量关键事件帧，避免排队分析旧图；用户提问/打断不能丢，短暂错误/成功提示不能只因出现新帧就无条件覆盖 |
| Agent理解 | 读取选中的新画面，判断是否推进、纠错或需补图；必要时再看局部细节 | 接收图片不等于已理解；不能仅凭像素变化、鼠标点击或静止就宣布成功 |

例如用户拖动窗口时，本地可以检测多次变化，通常等停稳后再让Agent看新图；打开导出面板后，给一张稳定图并续接；用户读说明、画面不变时，通常不需要新的模型读图；出现短暂错误提示则应保留对应事件证据。这里的次数只是情境说明，不承诺“每步恰好一张”。

筛选存在漏看小变化、把无关动画当变化、错过短暂提示的取舍；触发阈值、节流/最大等待及必要的补看策略要用真实任务验证。不能为了省读图而悄悄退回过期画面，也不能把普通聊天Agent描述成自动订阅视频的常驻视觉服务。现有Agent的正确会话唤醒/投递仍需独立打通，光增加截图循环不能解决。

相对于用户主动发问才附图，自动跟随会增加图像分析工作；合并和去重能减少重复，但具体调用次数、费用和时延尚未测量。下一次真实实验应同时记录本地采集次数、提交给模型的图像数、误触发/漏触发，以及有效指引的可见时延，再决定自动观察是否值得默认开启。

这与当前R32/ADR-023“不按固定间隔抓屏”的按需工具规则有差别，实施前应明确限定到用户开启的共享会话。不能通过改skill暗中扩大权限，也不能把已有lesson权限直接解释为无限连续共享。采集范围、开始/暂停/结束状态需可见；暂停停止后续采集/传输并丢弃未发观察，已发送的内容无法因此撤回。

每条屏幕指引需关联共享范围、画面版本和当前教学步骤。滚动、布局变化、切换范围或新问题到来时，旧坐标不能继续指向原位置。用户画板仍独立保留，撤销Agent指引不清用户笔迹。只有看过足够新的画面才能报告步骤完成，传输ack不等于视觉分析完成。

## 能否真的像会议，取决于响应节奏

T50历史的两轮有效样本为：消息到首句CLI返回约34.9秒、到指引命令返回约87.1秒（含约20.5秒截图审批），第二轮直接回答约12.8秒。它们包括Agent、工具与审批等待，未测可见首帧，也不是本轮重测或稳定性能分布。只换工具条无法证明会议式体验。

建议分别测：用户动作到本地可见反馈、稳定画面到第一条有用指引、插话到旧播报/指引停止。试验目标可先设为本地反馈/停止约200ms内，普通单步的有用指引中位数约2秒且P95约5秒；这是待验证的体验预算，不是现有承诺。不用“已收到”冒充有效建议，不用预制应答隐藏长等待。

当前CLI收发与T28尚待验证的宿主唤醒不足以证明任意Agent都支持实时续接和打断。建议先复用现有Agent验证关键帧续课；若实际仍需十几秒以上，把产品如实呈现为“看屏辅助”。会议级语音可能需要常驻、可取消、可流式回应的运行通路；是否引入新的实时模型服务或第二个Agent涉及R01/R30边界，另立决策，不在本提案中默认选定。

## 最小落地顺序

1. **先验证节奏。** 用同一导出任务对比当前流程与合成演示；观察用户能否理解共享、自己试试、暂停，以及是否仍想回聊天框确认。演示事件是预设，不验证识屏或推理速度。
2. **再做真实看屏续课的窄实验。** 选择一个屏幕和一段明确任务，打通授权、关键帧、现有Agent接收、步骤完成判断和过期指引撤销。先用短文字/按住说话，仍然只有一个输入面。复用T28/T47的验收边界，不把已知可靠性问题藏在新界面后面。
3. **证据足够后加入语音输出与打断。** 开放麦克风为可选能力，麦克风状态独立可见；验收回声、自触发、用户打断、取消和设备释放，再讨论会议式默认体验。

真实试验至少同时记录：同任务完成率与时间、为了推进而点击“下一步”的次数、错误续接/错误提醒次数、有效指引可见时延、打断停止时间，以及共享/暂停状态是否被正确理解。用相同任务复杂度、相同权限条件进行对照，不能以回复数更少就判定更好。

## 与现有决议的差异及待讨论项

| 既有边界 | 候选变化／需决定的事项 |
| --- | --- |
| R02/R22：say自动展开、三档对话面板 | 共享中默认短提示，历史按需打开；需明确哪些消息仍展开及草稿保护规则 |
| R03/R12：按住录音、转写提交 | 先保留；开放麦克风、语音输出和打断另验，不把wait当监听 |
| R09/R32：单次capture审批与按需取证 | 会话共享需单独清晰授权；范围、关键帧触发、暂停与撤回边界需接受 |
| DESIGN-NOTES：不做滚动自动失效 | 持续共享下建议撤销过期定位；需后续ADR明确取代旧约定 |
| R01/R30/R34：只指不做、复用现有Agent、宿主无关 | 保留；实时通路若需要新服务或新的会话所有者，另立决策 |

## 可测验收草案

日期：2026-11-04。本节是落盘时补上的草案句子，供以后拆任务时对照。它不改变上文的讨论状态，不把候选体验写成已接受的 PRODUCT 条款，也不把 Windows 远控、持续共享或实时语音记成已经验收。

这些句子对齐并且不改写已经接受的边界：

- [R14](PRODUCT.md)：远控／屏幕共享可见性可配置；面板、画布、HTML 使用统一开关并持久化；应用自身取图时排除自己的窗口。
- [ADR-005](DECISIONS.md#adr-005--接受--2026-10-17--远控可见性)：`showInScreenCapture` 缺省继续保护。打开后关闭面板、画布与 HTML 的内容保护，保存后立即生效，新 HTML 继承。该开关不决定 Agent 截图是否包含指引。不安装虚拟显示驱动，不保证所有第三方采集方案；真实客户端画面须另验。
- [ADR-007](DECISIONS.md#adr-007--接受--2026-10-17--取消取图显隐与真实-cli-验证)：取帧前对面板、画布、HTML 临时启用系统捕获排除，finally 恢复用户的远控可见设置；不隐藏窗口、不改焦点。不能只用 `isContentProtected` 推断画面已经排除。取图同时受 [R15](PRODUCT.md) 约束，不能退回 hide/show。
- 指引是否接住点击，跟 [R07](PRODUCT.md)、[R08](PRODUCT.md) 同一条线：指引穿透、不抢焦点；只有编辑时画布接收鼠标。对方看不看得见（R14）和点击会不会被挡住，是两件分开的事。

下面每条都是「过 / 不过」草案。写出「过」不等于本仓库已经观察到该结果。

### 远控／共享时面板对对方是否可见

- 过：开关关闭（含旧配置缺省）时，对方的远控或屏幕共享画面里看不到 teach-me 的面板、画布和 HTML。开关打开并保存后，对方能看见这三类窗口，并且之后新建的 HTML 使用同一设置。
- 不过：对方看见或看不见的结果与当前开关不一致；只打开了其中一类窗口；或者只根据本机 `isContentProtected`、本机自截图就判断对方客户端里已经看见或看不见。ADR-005 与 ADR-007 要求真实客户端画面另行验证。本草案没有把该验证记成已经完成。

### Agent 取图是否排除 teach-me 自己的面板／指引层

- 过：Agent 取图得到的画面里没有 teach-me 自己的面板、画布和指引层（含 HTML）。取图开始时临时排除这些窗口，成功或失败都在结束时恢复用户原来的远控可见设置。取图过程不靠隐藏再显示窗口。
- 不过：取到的图里出现自己的面板或指引；取图结束后远控可见设置仍停在临时排除，没有恢复；或者把「远控开关打开」理解成 Agent 截图应当带上指引。ADR-005 写明该开关不决定 Agent 截图是否包含指引。

### 指引是否挡住对方操作

- 过：未进入画板编辑时，对方通过远控点在指引或画布所在区域，点击落到目标软件，不落到 teach-me 指引层，指引也不抢走焦点。进入编辑后画布可以接收本机鼠标；退出编辑后穿透恢复。
- 不过：未编辑时对方的点击被指引、画布或 HTML 吃掉；或者用「对方画面里看不见面板」代替穿透检查。内容保护只影响采集，不代替命中测试。

### 失败／边界时给用户什么可见反馈

- 过：暂停共享、连接中断、切换共享范围、取图失败或当前画面已不能沿用时，用户能看见一句明确状态。候选文案是「共享已暂停」或「连接中断」，具体用词留到接受提案后再锁定。同时撤下旧指引，不再显示「我正在看」，也不把还没看完的观察说成已经看懂。恢复之后先取新画面，再给下一步。
- 不过：上述边界发生后界面没有可见文案，旧箭头仍指着过期坐标，或只用「已收到」代替状态。安静失败不算过。

本小节不用 T51、T52 的恢复文案（「正在恢复，稍等」「这句没发出去」「面板恢复失败，请重新打开。」）充当共享屏幕的失败反馈。那些句子属于恢复切片，而且该切片仍是 in_progress。共享屏幕提案未实现。
